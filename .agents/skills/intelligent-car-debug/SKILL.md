# 智能车控制调试

## 目标

以证据为基础定位智能车控制问题，优先找到真正的控制链路和根因，再进行最小、可验证、可回退的修改。不要用无依据的 PID 猜值代替分析。

默认使用用户当前使用的语言回答；用户未指定时使用中文。

## 基本原则

1. 先读仓库根目录及当前目录链上的 `AGENTS.md`、README、硬件说明和已有调试记录。
2. 先分析，后修改。除非用户明确要求直接修改，否则先给出诊断结论和修改方案。
3. 不凭变量名猜含义。通过定义、赋值、调用链和最终执行位置确认变量的真实作用。
4. 不只检查 PID 参数；必须同时检查控制周期、单位、符号、坐标系、滤波、限幅、死区、饱和、积分、状态机和执行器混控。
5. 一次只改变一个主要机制或一小组强相关参数，避免同时修改多个控制环导致无法归因。
6. 保留原有项目架构和驱动接口。不得擅自更换 MCU 引脚、定时器、编码器方向、底层驱动、通信协议或车辆坐标定义。
7. 任何物理测试都先给出安全限制：低速、留出急停、必要时架空车轮、限制输出，并避免在人或易损设备附近测试。
8. 所有结论分为“代码已证实”“日志/数据支持”“合理推测”三类，不把推测写成事实。

## 工作模式

根据用户请求选择模式：

- **只分析**：阅读代码和资料，定位原因，不改文件。
- **修改代码**：先说明根因和最小改动，再实施修改并验证。
- **参数整定**：设计分阶段实验，不直接一次给出最终参数。
- **代码审查**：检查控制实现、风险和可测试性，不进行无关重构。
- **测试设计**：给出变量记录、测试顺序、通过标准和风险控制。

用户未明确时，默认采用“只分析”，除非任务显然要求修复代码。

## 调试流程

### 1. 明确现象和边界

从用户描述、视频结论、日志、波形或代码中提取：

- 车辆类型：麦轮、差速、舵机车、平衡车、独轮车或其他。
- 故障发生阶段：启动、加速、直行、转弯、目标切换、刹停、倒车或模式切换。
- 现象：超调、不足、振荡、跑偏、打滑、响应慢、突然跳变、饱和、丢目标或重复动作。
- 复现条件：速度、负载、电池电压、地面、方向、控制模式和出现概率。
- 用户目标：更快、更稳、更准，还是保留速度通过。

缺少信息时，先从仓库和已有数据中尽量推断；不要因为信息不完整而停止工作。对关键假设明确标注。

### 2. 重建完整控制链路

必须找到并写出实际链路：

`传感器/视觉输入 → 校准与滤波 → 状态估计 → 目标生成 → 速度/位置/姿态/转向控制器 → 运动学混控 → 限幅与死区 → 电机驱动 → 车辆`

同时确认：

- 每个环的调用位置和真实执行周期。
- 目标量、反馈量、误差、控制器输出和最终 PWM/电流命令。
- 单位与量纲，例如 m/s、编码器计数/周期、deg、rad、deg/s、PWM。
- 正方向、左右轮方向、车体坐标和世界坐标。
- 数据类型、缩放倍率、整数截断、溢出和符号转换。
- 控制器输出是否被后续逻辑覆盖、二次限幅或重新混控。
- 模式切换、S/R 状态、标志位和中断/主循环之间的数据更新关系。

先用简洁文本或流程图式描述控制链，再判断参数。

### 3. 检查时序和离散实现

优先检查以下问题：

- 代码设定周期与实际周期是否一致。
- PID 中的积分和微分是否正确包含 `dt`，参数是否按当前周期整定。
- 控制循环是否抖动、丢周期或被阻塞操作拖慢。
- 视觉帧率和控制周期是否不同步，是否重复使用旧目标。
- 滤波是否引入过大延迟。
- 编码器是否每周期清零，速度换算是否和采样周期匹配。
- 多个控制环的频率层级是否合理，内环是否明显快于外环。
- 共享变量是否需要 `volatile`、原子读取或临界区。

### 4. 检查控制器本体

对每个控制环分别确认：

- 控制对象和反馈量是否匹配。
- P、I、D、前馈、静摩擦补偿分别在解决什么问题。
- 输出限幅和积分限幅是否合理。
- 饱和时是否发生积分累积，是否需要抗积分饱和。
- D 项来自误差差分还是直接传感器角速度，噪声和符号是否正确。
- 目标突变是否需要斜坡、S 曲线、加速度或加加速度限制。
- 死区补偿是否在零点附近造成跳变或左右不对称。
- 前馈和反馈是否重复补偿同一作用。
- 串级控制中，外环输出是否处于内环可实现范围内。

不要看到超调就直接减小 `Kp`，也不要看到响应慢就直接增大 `Kp`。先判断是目标规划、延迟、饱和、积分、机械打滑还是控制器增益导致。

### 5. 检查车辆特有部分

按车辆类型读取并使用 `references/control-checklist.md` 中对应章节：

- 麦轮：车体速度到四轮速度的运动学、轮序、符号、归一化、轮速饱和、横移与旋转耦合。
- 差速/舵机车：线速度与转向分配、曲率、转向饱和、左右轮差速和舵机非线性。
- 平衡/独轮：姿态内环、速度外环、机械零点、陀螺仪方向、启动和停车过程。
- 视觉控制：坐标变换、目标跳变、帧延迟、置信度、目标保持和切换状态机。

### 6. 建立根因优先级

输出最多 3 个主要候选根因，并按证据强弱排序。每个候选必须包含：

- 支持证据。
- 与现象的因果链。
- 如何用最小实验区分它与其他原因。
- 若成立，应修改哪里。
- 修改可能带来的副作用。

若代码中已经存在确定性错误，直接指出文件、函数、变量和调用关系，不要被 PID 调参分散注意力。

### 7. 制定最小修改

修改前先列出：

- 目标行为。
- 需要修改的文件和函数。
- 保持不变的接口和参数。
- 成功判据。
- 回退方式。

修改时遵守：

- 不进行与问题无关的大规模重构。
- 保留必要注释，说明单位、周期、符号和限幅原因。
- 新增参数集中定义，避免魔法数字散落。
- 对目标跳变优先增加明确的规划或限速机制，而不是用低通滤波掩盖所有问题。
- 对饱和和死区问题优先修复约束逻辑，而不是只增大控制增益。
- 对多个轮子表现不同的问题，先区分机械、电气、编码器和软件方向，不用四套独立 PID 掩盖硬件问题。
- 不删除已有安全保护、急停、输出限幅或故障处理。

### 8. 验证

能运行项目工具时，依次执行：

1. 查看修改差异。
2. 运行格式、静态检查或编译。
3. 检查编译警告，尤其是隐式类型转换、溢出、未使用变量和符号问题。
4. 搜索修改变量的全部读写位置，确认没有遗漏或被覆盖。
5. 若仓库包含仿真、回放数据或单元测试，运行相关测试。
6. 无法编译或缺少硬件时，明确写出未验证部分，不声称“已经解决”。

物理测试按 `references/test-plan.md` 设计，至少包含低风险测试、记录变量、通过标准和下一步决策。

## 常见行为的诊断顺序

### 超调或冲过目标

依次检查：

1. 目标减速是否开始过晚，规划距离是否足够。
2. 执行器是否饱和，实际减速度是否达不到规划值。
3. 视觉或传感器延迟。
4. 积分累积和目标切换时积分是否清理。
5. 速度估计滤波延迟。
6. P/D 参数和离散周期。
7. 打滑导致里程计与真实位移不一致。

### 响应不足或到不了目标

依次检查：

1. 输出限幅、死区、静摩擦和电池电压。
2. 目标是否被斜坡或滤波限制。
3. 轮速命令归一化是否过度缩小。
4. 反馈单位或缩放是否错误。
5. P/前馈不足。
6. 积分被禁用或限幅过小。
7. 机械阻力或单轮异常。

### 振荡

依次检查：

1. 控制周期、符号和 D 项方向。
2. 传感器噪声和微分放大。
3. 内外环带宽过近。
4. 死区补偿造成零点跳变。
5. 输出饱和与积分来回释放。
6. 机械间隙、结构共振或轮胎弹性。
7. 参数过激。

### 打滑

依次检查：

1. 目标加速度和加加速度是否过大。
2. 前后轮或左右轮是否同时达到饱和。
3. 地面、轮胎、重心和载荷。
4. 麦轮横移/旋转时的轮速分配。
5. 编码器速度与惯性/视觉速度是否出现短时偏离。
6. 是否把打滑造成的误差继续通过积分放大。

不要仅凭编码器看不出异常就判定没有打滑，因为驱动轮打滑时编码器仍可能显示“正常轮速”。

## 参数整定规则

进行调参时：

1. 先固定机械状态、电池电压范围、地面和载荷。
2. 先保证传感器、方向、单位、周期、限幅正确。
3. 先内环后外环，先低速后高速。
4. 一次只改变一个主要参数。
5. 每次记录旧值、新值、现象、数据和结论。
6. 使用可量化指标：上升时间、超调量、稳定时间、稳态误差、最大输出、饱和时间、路径误差、航向误差和滑移迹象。
7. 不把某一次“看起来不错”当作完成；至少在多个方向或多次重复测试中验证。
8. 参数建议优先给调整方向、幅度范围和判据，不编造看似精确的最终数值。

## 输出格式

最终回复按任务需要包含以下内容，保持简洁但信息完整：

### 结论
一句话说明最可能的根因和当前置信度。

### 控制链路
列出与问题直接相关的输入、控制器、混控、限幅和输出路径。

### 证据
区分代码已证实、数据支持和合理推测。

### 修改
列出文件、函数、具体变化和为什么这样改；未修改时给出建议修改点。

### 验证
说明执行过的编译/测试、未验证部分、上车测试步骤和通过标准。

### 风险
指出修改可能导致的超调、响应变慢、饱和、发热、打滑或模式切换风险。

## 完成标准

只有满足以下条件才可声称任务完成：

- 已定位真实控制链路，而不是只根据变量名猜测。
- 已检查周期、单位、符号、限幅、死区和状态切换。
- 修改范围与根因直接相关。
- 已完成可用的静态验证或明确说明无法验证。
- 已给出可复现、可量化、低风险的测试方法。
- 未把未经实车验证的结果描述为“已经彻底解决”。
